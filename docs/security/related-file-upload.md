# ファイルアップロード機能 セキュリティガイドライン

## 1. 概要
本ドキュメントは、Webアプリケーションにおけるファイルアップロード機能の実装時に考慮すべきセキュリティリスクとその対策をまとめたガイドラインです。不適切な実装は、サーバーの乗っ取りや個人情報の流出など、深刻な被害を招く可能性があります。

## 2. 想定される主な脅威
ファイルアップロード機能には、以下のような多様な攻撃リスクが潜んでいます。

*   **Remote Code Execution (RCE):** サーバー上で任意のコード（OSコマンド等）を実行される、最も深刻な攻撃の一つです。
*   **MIME Sniffingによる脆弱性:** ブラウザがファイル内容からMIMEタイプを推測する挙動を悪用し、偽装した悪意あるファイルをスクリプトとして実行させます。
*   **パストラバーサル攻撃:** 細工されたファイル名により、意図しないディレクトリへの保存や重要ファイルの書き換えを狙います。
*   **画像処理ライブラリの脆弱性悪用:** `ImageMagick`や`libpng`などの古いバージョンの脆弱性を突き、任意のコード実行やDoS攻撃を仕掛けます。
*   **Polyglot File Attack:** 複数のファイル形式として解釈可能なファイルを作成し、セキュリティチェックを回避します。
*   **その他:** 蓄積型XSS、WebShellのアップロード、メタデータインジェクション、NULLバイト攻撃など。

## 3. 実装のベストプラクティス

### 3.1 サーバーサイド対策の徹底
*   **前提条件:** フロントエンドでの対策はあくまで「補助的」なものです。根本的な安全性を確保するためには、**サーバーサイドでの対策が必須**です。

### 3.2 厳密な検証とサニタイゼーション
*   **マジックバイトによる検証:** ファイルのヘッダー情報を確認し、実際のファイル形式を検証します。
*   **拡張子の許可方式（ホワイトリスト）:** 許可する拡張子のみを定義し、それ以外は拒否します。
*   **厳密なファイル名検証:** 正規表現による検証は回避される可能性があるため、完全一致やRFC標準仕様に準拠した検証を行います。
*   **ライブラリの活用:** 信頼できるライブラリを用いて、ファイル名やMIMEタイプを安全な形式に正規化・サニタイズします。

### 3.3 レスポンスヘッダの設定
*   **X-Content-Type-Options:** `nosniff` を指定し、ブラウザによる自動的なMIMEタイプの推測を防止します。これにより、サーバーが指定したContent-Typeを厳密に適用させます。

### 3.4 配信環境の分離
*   **ドメインの分離:** アプリケーション本体（例: `example.com`）とファイル配信専用（例: `user-content.com`）でドメインを分離します。
*   **効果:** 万が一XSS等の脆弱性が発生しても、攻撃者がセッションCookieや認証情報を窃取することを困難にし、被害範囲を最小限に抑えられます。

### 3.5 サーバー環境の保護
*   **実行権限の制限:** アップロードされたファイルが保存されるディレクトリでは、スクリプトの実行権限を無効化します。
*   **ライブラリの更新:** 画像処理ライブラリを常に最新の状態に保ちます。
*   **ウイルススキャン:** アップロード時にウイルススキャンを実施することを推奨します。
