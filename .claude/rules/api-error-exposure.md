# API エラー情報露出防止規約（必須）

## 対象範囲
本ルールは、すべての API エラーレスポンスに適用される。

- Next.js Route Handler（`app/api/**/route.ts`）
- Server Action
- HTTP レスポンスを返すサーバー処理

---

## 絶対ルール（違反禁止）

### 1. 生のエラーオブジェクトをクライアントに返してはならない
内部エラー情報をそのままレスポンスとして返すことを禁止する。

❌ 禁止例：
```ts
catch (e) {
  return NextResponse.json(e, { status: 500 });
}
````

---

### 2. スタックトレース・内部メッセージを露出してはならない

以下の情報は **クライアントに返却してはならない**。

* スタックトレース
* データベースエラーメッセージ
* AWS / Lambda / SDK の内部エラー
* SQL 文・テーブル構造
* ファイルパス・内部構成

---

### 3. エラーレスポンスは必ずサニタイズする

クライアントに返すエラーは **安全で抽象化された内容のみ**とする。

✅ 必須：

```ts
catch (e) {
  console.error("内部エラー:", e);

  return NextResponse.json(
    { error: "Internal Server Error" },
    { status: 500 }
  );
}
```

---

### 4. 想定内エラーと内部エラーを混同しない

入力不正・権限不足などの想定内エラーでは、
内部エラー表現を使用してはならない。

```ts
return NextResponse.json(
  { error: "権限がありません" },
  { status: 403 }
);
```

---

### 5. エラー詳細はログにのみ出力する

* クライアント → 抽象化されたメッセージ
* サーバーログ → 完全なエラー情報

---

## 実装前セルフチェック（必須）

* [ ] エラーオブジェクトをそのまま返していない
* [ ] 内部情報をレスポンスに含めていない
* [ ] エラー詳細はログにのみ出力されている
* [ ] クライアント向けメッセージは安全である

---

## このルールの背景

> **エラーは開発者のためのものであり、攻撃者のためのものではない**

エラー情報の露出は以下を引き起こす：

* 内部構造の推測
* 攻撃ベクトルの特定
* 脆弱性探索の容易化

---

## 運用上の扱い

本ルール違反は以下として扱う：

* セキュリティインシデント
* マージブロッカー
* 即時修正対象
