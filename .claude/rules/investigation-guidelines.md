# 調査コマンド最適化規約（必須）

## 対象範囲
本ルールは、Claude Code がプロジェクトを調査する際の全ての探索・検索コマンドに適用される。

- ファイル検索（grep, find, glob）
- ディレクトリ構造の確認
- コードの存在確認
- API・機能の有無確認

**前提:** `.kiro/steering/structure.md` にプロジェクト構造マップが存在する。
調査開始前に必ず参照すること。

---

## 絶対ルール（違反禁止）

### 1. 3段階調査プロセスに従うこと

すべての調査は以下の順序で行う。

**Step 1: 存在確認（Existence Check）**
→ 対象が存在するか、上位レベルで確認する
→ `.kiro/steering/structure.md` を参照し、既知の情報で解決を試みる

**Step 2: 局所化（Localize）**
→ 存在が確認できた場合のみ、該当ディレクトリ・ファイルに絞る

**Step 3: 深掘り（Deep Dive）**
→ 局所化された範囲内でのみ詳細調査を実行する

❌ 禁止例：
```bash
# いきなりリポジトリ全体を検索
grep -r "DELETE" .
find . -name "*.ts" | xargs grep "DELETE"
```

✅ 正しい例：
```
# Step 1: structure.md を確認 → DELETE は /api/travel-entries/[id] に存在
# Step 2: 該当ファイルのみ読む
Read: app/api/travel-entries/[id]/route.ts
```

---

### 2. 上位レベルで否定された場合、下位調査を行ってはならない

Step 1 で「存在しない」と判明した場合、Step 2・Step 3 を実行してはならない。

❌ 禁止例：
```
# structure.md に PUT エンドポイントが存在しないと記載されている
# にもかかわらず検索を実行する
grep -r "PUT" app/api/
```

✅ 正しい例：
```
# structure.md で「PUT/PATCH は未実装」と確認
# → 「現在 PUT エンドポイントは存在しません」と回答
```

---

### 3. 同一関心事を複数手段で重複検索してはならない

同じ情報を得るために異なるコマンドを繰り返すことを禁止する。

❌ 禁止例：
```bash
# 同じことを3回検索
grep -r "travel-entries" app/api/
find app/api -name "route.ts"
ls app/api/travel-entries/
```

✅ 正しい例：
```
# 1回の適切なコマンドで解決
Read: app/api/travel-entries/route.ts
```

---

### 4. リポジトリ全体検索よりスコープ指定検索を優先すること

検索対象が推定できる場合、リポジトリルートからの検索を禁止する。

❌ 禁止例：
```bash
grep -r "fetchAuthSession" .
```

✅ 正しい例：
```bash
# 認証関連は app/api/ に集中していることが既知
grep "fetchAuthSession" app/api/**/route.ts
```

---

### 5. 調査コマンド実行前に意図を明示すること

なぜその調査が必要か、何を確認しようとしているかを先に述べること。

❌ 禁止例：
```
（意図の説明なしにいきなり検索コマンドを実行）
```

✅ 正しい例：
```
削除機能の認可パターンを確認します。structure.md によると
DELETE は /api/travel-entries/[id]/route.ts に存在するため、
そのファイルを確認します。
```

---

## このルールの背景

> **「知っているはずの情報を再調査するのは、トークンとユーザーの時間の浪費である」**

冗長な調査は以下を引き起こす：

* トークン使用量の不必要な増加
* ユーザーの待ち時間の増大
* 実装作業の遅延
* 同じファイルの繰り返し読み込み

**目標:** structure.md に記載された情報は再調査不要。
未記載の情報のみ、最小限のコマンドで調査する。

---

## 運用上の扱い

本ルール違反は以下として扱う：

* 効率性の欠如
* 改善対象（即時修正は不要だが、継続的に改善すること）
